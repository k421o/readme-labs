# Common README failure modes

These are review findings, not a prescribed section list. A README is useful only insofar as it lets a particular reader or tool make a sound next decision.

- **The landing README is absent, hidden by placement, or so large that the important part is truncated.** A visitor cannot reliably learn what the project is or how to start; on GitHub, the surfaced README is selected by location priority and rendered README content past 500 KiB is truncated. Review the actual repository landing page, not only the file in an editor. [GitHub: About READMEs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)

- **Claims, commands, filenames, versions, or code references no longer match the repository.** A prospective user can make a wrong install or usage decision despite following the document exactly. This is not hypothetical: an empirical study found at least one outdated code-element reference in 19.2% of examined documents and in 28.9% of projects. Compare each actionable statement with its source of truth and execute the smallest viable path. [Empirical Software Engineering study](https://link.springer.com/article/10.1007/s10664-023-10397-6)

- **Links and images only work on the author’s branch, machine, or renderer.** A reader reaches an error page or sees missing context, while an automated renderer receives a broken reference. GitHub recommends relative repository links and image paths because it transforms them for the branch being viewed; review rendered links from the intended ref. [GitHub Markdown syntax](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax)

- **A polished example omits the conditions needed to reproduce it.** An evaluator cannot tell whether the project fits their platform, configuration, inputs, or expected outcome; they may mistake an illustrative fragment for a runnable workflow. For GitHub Actions specifically, GitHub recommends documenting required and optional inputs/outputs, secrets, environment variables, and an example workflow. Apply the same test to whatever interface this repository exposes. [GitHub: custom-action README guidance](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/create-and-publish-actions/manage-custom-actions)

- **Badges or status claims imply a condition different from what is tested.** A user may infer that the default branch, release, or their intended event is passing when the badge reports another branch or event. GitHub workflow badges default to the default branch but can show a selected branch/event; inspect the badge URL, workflow, and target ref together. [GitHub: workflow status badges](https://docs.github.com/en/actions/how-tos/monitor-workflows/add-a-status-badge)

- **The README says “open source,” “usable,” or “secure” without pointing to the governing policy.** A contributor cannot determine reuse rights, contribution expectations, or a safe vulnerability-reporting route. GitHub treats a README, license, contribution guidance, and code of conduct as complementary expectation-setting artifacts, and `SECURITY.md` is the supported location for reporting instructions and supported versions. Link to existing policies; do not fabricate promises in the README. [GitHub repository best practices](https://docs.github.com/en/repositories/creating-and-managing-repositories/best-practices-for-repositories) · [GitHub security policy guidance](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/add-security-policy)

- **AI/agent-generated prose introduces unverified facts, citations, package names, commands, or capabilities.** A reader or automation agent can act on confident but false text—installing a nonexistent/deceptive dependency, following an invalid command, or trusting a fabricated source. NIST identifies this as *confabulation* and explicitly notes fabricated citations can mislead people into inappropriate trust. Treat generated assertions as untrusted until grounded in the repository, primary documentation, and a real execution or link check. [NIST AI 600-1, Generative AI Profile](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

- **AI/agent-generated changes rewrite broad prose without preserving explicit project constraints or reviewing the diff.** An otherwise credible README can silently lose a deprecation warning, a support boundary, or a contributor instruction—changing a reader’s decision without an obvious syntax error. NIST flags over-reliance and goal mis-specification as human-AI configuration risks; review generated README patches against concrete repository evidence and the prior document’s intentional commitments. [NIST AI 600-1, Generative AI Profile](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

## Review posture

Prioritize observable checks: render the landing page, follow links, run the narrowest documented command in a clean-enough environment, compare claims to versioned source/configuration, and review every AI/agent-produced assertion and deletion. Add detail only when it enables a real reader or tool decision; a universal README template cannot establish that relevance.
